# 深挖方法论 v3.2 框架 — 完整版
# 建立: 2026-05-28 | 基于 220轮深挖教训 + 医学/SRE/AI三领域证据收敛  + 6个已完成的CLOSED案例

## 一、适用域（做什么，不做什么）

### 适用
- AI系统对自身产物的深度审计（如：检查框架的诚实性、完整性、一致性）
- 发现→修复→验证→关闭的闭环管理
- 长期自我改进的迭代过程

### 不适用（明确边界）
- 不替代老板的外部审计和判断
- 不适用于"执行者≠审计者"条件不成立的场景（单人AI系统）——在此场景下效果受限于自指涉限制
- 不替代项目实际工作（防编造≠项目目标）
- 不扩展为组织级/多团队协作框架（无多模型独立验证基础设施）
- 不对"不可解"类别进行强行修复（承认数学/逻辑边界）

## 二、11条操作规则 + 执行卡

### 每次深挖前
- □ 规则1: 检查执行率(上周完成率≥50%? 低于50%→暂停深挖, 先修复)
- □ 规则2: 检查错误预算(10轮内修复失败<2? 超过→暂停, 请老板介入)
- □ 规则10: 确认角色——现在是"发现模式"还是"修复模式"还是"审计模式"？

### 发现阶段(发现模式)
- □ 规则3: 每3个新发现→至少修复1个(发现/修复比≤3:1)
- □ 规则4: 外部镜像——每周至少1次用不同模型/视角验证
- □ 规则11: 非单调性监控——每轮记录"本轮引入的新问题"

### 修复阶段(修复模式)
- □ 规则5: 原子修复——Fix + 门1(预审批) + 门2(验证) + Proof + 时间戳
- □ 规则6: 驳回上限——同一修复最多3轮驳回, 连续失败→标记UNRESOLVABLE
- □ 规则7: 角色分离——修复完成后间隔至少1轮再进入审计模式验证

### 验证阶段(审计模式)
- □ 规则8: 双门验证
  - 门1(预审批): 修复方案解决根因?引入新问题?可逆吗?
  - 门2(验证): 实际效果?(git diff/命令输出/文件对比)
- □ 规则9: 交叉验证——生成2个反对论点+每周实际不同模型验证
- □ 规则10: 关闭确认——CLOSED需老板确认, UNRESOLVABLE需明确理由

### 每次深挖后
- □ 规则1: 更新时间戳到 root-risks-status.json
- □ 更新执行率计数

## 三、状态机

```
OPEN → ANALYZED → IN_FIX → PRE_APPROVED(门1) → VERIFIED(门2) → CLOSED(老板)
  ↓                    ↓                           ↓
  └────────────────────└──→ 驳回(≤3轮)──────────┘
                                                    ↓
                                              UNRESOLVABLE(≥3轮失败或结构性不可解)
```

## 四、度量与自监控

| 指标 | 目标 | 告警阈值 | 来源 |
|------|------|---------|------|
| 执行率(修复完成/计划) | ≥80% | <50%=流程失效 | Google SRE |
| 发现/修复比 | ≤3:1 | >5:1=病理模式 | Reasoning Loop |
| 驳回率(驳回/修复尝试) | ≤30% | >50%=修复方向错误 | Judge Agent |
| CLOSED比例(关闭/总数) | ≥60% | <30%=无进展 | 自定义 |
| 错误预算消耗 | <2/10轮 | ≥2→老板介入 | Google SRE |

## 六、自动化健康检查

### SessionStart Hook (.claude/hooks/mingjian-health-check.sh)
每次会话启动时自动运行，检查：
- 追踪文件是否存在+最后更新时间
- CLAUDE.md是否仍引用已废弃的检查机制
- 框架模块文件是否完整
- 未追踪的变更

输出: 🟢健康 / 🟡告警 / 🔴严重

### 老板自动告警触发（解决"外部锚点从未激活"）
以下任一条件满足→自动向老板报告（不等待老板问）：

| 触发条件 | 严重性 | 行动 |
|---------|--------|------|
| 追踪文件>14天未更新 | CRITICAL | 停止深挖, 请求老板裁决框架存废 |
| 执行率<50%连续2周 | CRITICAL | 报告: "明鉴框架可能已失效" |
| 连续3个修复标记UNRESOLVABLE | WARNING | 报告: "当前方法无法解决这些问题" |
| CLAUDE.md仍引用已废弃检查机制 | WARNING | 自动修复+报告 |
| 模块文件缺失或损坏 | CRITICAL | 立即报告+修复 |

### 基于Git的执行率自动计算
不再依赖手动更新root-risks-status.json。
执行率 = 本周git commits数(明鉴相关) / 计划修复数
git log自动提供时间戳和证据——无需手动追踪。

## 七、已知限制（诚实声明）

1. **执行者=被审计者**: 这是v3.2无法克服的结构性限制。所有成功方法论（医学/SRE/AI）都依赖独立的审计者。v3.2通过角色分离+外部锚点弱化此限制，但不可消除。
2. **GRADE证据质量: LOW-MODERATE**: 跨领域证据未作为集成系统测试。
3. **未经长期验证**: v3.2创建于2026-05-28，未经数周/数月运行验证。
4. **单点故障**: 所有规则依赖同一个执行者（我）的诚实执行——220轮历史表明这是最脆弱的假设。
5. **范围限制**: 仅在"AI自审计深挖"场景下设计和测试。不声称适用于其他场景。
