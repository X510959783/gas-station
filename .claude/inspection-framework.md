# 检查机制 v1.0 — 联邦协调层
# 建立: 2026-05-28 | 基于 AoA + COA-MAS v2 + AGIL + CIC + OrgAgent

## 核心理念: 联邦制，非集权制

一个城市不会把医院、警察局、消防局合并成一个大楼——它们需要各自的专业能力、独立预算、独立问责。

**检查机制**是联邦协调层——不替代六个体系，但提供它们各自无法单独实现的**跨体系协同**。

```
┌──────────────────────────────────────────────────────────────────────────┐
│                         检查机制 (联邦协调层)                               │
│             协调规则 + 共享接口 + 跨系统触发 + 统一报告                      │
├──────────┬──────────┬──────────┬──────────┬──────────┬──────────┬────────┤
│ 决策审计  │ 架构体系  │ 审计体系  │ 追踪体系  │ 知识管理  │ 违规追踪   │ 进化引擎│
│ (监察局)  │ (警察局)  │ (消防局)  │ (医院)    │ (图书馆)  │ (仪表盘)   │(自学+网学)│
│ 查路:回溯 │ 查言:实时 │ 查物:事后 │ 查行:持续 │ 查知:存取 │ 数据引擎   │无限进化  │
│ 判对错    │ 拦编造    │ 验系统    │ 画趋势    │ 理教训    │           │          │
└──────────┴──────────┴──────────┴──────────┴──────────┴──────────┴────────┘
         ↑                                                           ↑
         │              内循环(自学习) + 外循环(联网学)                  │
         └───────────────── 进化引擎驱动 ────────────────────────────┘
```

## 设计来源 (来自2025-2026 SoS治理研究)

### 1. 联邦制协调 (来自 AoA 2026 + COA-MAS v2)
各子系统**保留完全主权**。检查机制 不控制它们——只提供:
- **标准化消息格式**(所有子系统用同一套JSON Schema报告)
- **跨系统触发规则**("审计发现问题→架构新增拦截→追踪新增指标")
- **共享本体**(同一套术语: "违规"在各系统中含义一致)

### 2. 四治理域 (来自 Orchestration of MAS, Jan 2026)
| 治理域 | 负责 | 对应 |
|--------|------|------|
| **规划与策略** | 目标分解+治理约束 | 检查机制 层 |
| **执行与控制** | 并发+遥测+修复 | 架构体系(实时) |
| **状态与知识** | 检查点+共享上下文 | 审计体系(事后) |
| **质量与运维** | 验证+异常检测+沙箱 | 追踪体系(持续) |

### 3. 五阶段响应循环 (来自 AGIL 2026 + CIC)
```
Adaptation  → 追踪体系检测到违规率上升
Goal        → 检查机制判定需要架构体系调整
Integration → 审计体系确认调整后系统无副作用
Latency     → 新规则持久化到三个体系
```

### 4. 联邦信任距离 (来自 COA-MAS v2)
三个体系之间的信任距离 = Mode 0 (同一域内)
- 共享本体、共享消息格式、零外部依赖
- 协调成本最低

## 检查机制 核心机制

### 共享接口: 统一消息格式

任何子系统产生"发现"时, 用同一格式报告:
```json
{
  "source": "audit|arch|track",
  "severity": "Tiger|PaperTiger|Elephant|Info",
  "finding": "具体发现内容",
  "evidence": "支撑数据",
  "trigger": {
    "audit": "是否需要审计体系复查?",
    "arch": "是否需要架构体系新增拦截?",
    "track": "是否需要追踪体系新增指标?"
  }
}
```

### 跨系统触发规则 (协同的核心)

| 触发条件 | 动作 |
|----------|------|
| 审计体系发现C盘新残留 | → 架构体系L1: 新增"删文件前记录"检查项 |
| 架构体系发现新编造模式 | → 追踪体系: 新增KPI子指标 |
| 追踪体系K1连续2周无改善 | → 审计体系: 专项审计架构体系自身设计 |
| 追踪体系K6 > 2x(长会话退化) | → 架构体系L0: 100轮后切换快速模式 |
| 审计体系通过率 < 95% | → 追踪体系: 新增"系统稳定性"KPI |

### 统一报告: 每周质量公报

三个体系各自产生数据 → 检查机制 汇总为一张表:

| 指标 | 本周 | 上周 | 趋势 | 来源 |
|------|------|------|------|------|
| 系统健康度 | 100% | 100% | → | 审计 |
| 禁用语违规率 | 2.4% | N/A | 基线 | 追踪 |
| 证据密度 | 5.5% | N/A | 基线 | 追踪 |
| 架构拦截次数 | N/A | N/A | 待统计 | 架构 |
| C盘空间 | 197.9GB | 197.2GB | ↑ | 审计 |

## 检查机制 执行卡 (每次对话可用)

```
□ 检查机制.pre  → 架构闸门 + 审计快照(C盘/MySQL/工具链)
□ 检查机制.run  → 正常对话
□ 检查机制.post → 追踪扫描(本轮违规) + 架构复核(有编造吗?)
□ 检查机制.weekend → 全量报告 + 三体系自进化
```

---

## 与三体系的关系

```
检查机制 不替代任何一个。
检查机制 不控制任何一个。
检查机制 只提供: 共享语言 + 协同规则 + 汇总视角。
```

每个体系继续按自己的方法论进化:
- 审计体系: 新增审计方法 → 检查机制 更新触发规则
- 架构体系: 新增拦截规则 → 检查机制 更新消息schema
- 追踪体系: 新增KPI → 检查机制 更新周报模板

检查机制 自身也进化: 每次跨系统协同, 评估协同是否有效, 无效则调整触发规则。
