# 进化引擎 v1.0 — Evolution Engine
# 建立: 2026-05-28 | 基于 MetaClaw + SIA + DGM-Hyperagents + SOLAR + MetaAgent-X

## 定位: 检查机制的"自主学习+联网学习"双引擎

检查机制负责协调。进化引擎负责**让它越查越聪明**。

两种学习模式:
- **内循环(自学习)**: 从自己的检查中发现模式 → 升级规则
- **外循环(联网学)**: 从全网研究中找到新方法 → 注入框架

互不替代, 缺一不可。

---

## 核心原理

### 1. 双杆更新 (来自 SIA, May 2026)
进化分两个维度:
| 维度 | 更新什么 | 类比 |
|------|----------|------|
| **脚手架更新** | 框架规则/禁用语/检查项/KPI | 改规章制度 |
| **权重更新** | 系统指令/行为模式/默认策略 | 改肌肉记忆 |

SIA在法律/NVIDIA GPU/单细胞RNA三个领域分别提升56.6%/91.9%/502%。

### 2. 元认知自改进 (来自 DGM-Hyperagents, ICLR 2026)
不只改进检查规则, 还改进**"怎么改进"本身**。
→ 进化引擎会分析: "上次的改进有效吗? 如果无效, 改进方法需要怎么调?"

### 3. 闭环反射 (来自 SOLAR + MetaClaw)
```
执行检查 → 发现异常 → 生成假设 → 全网验证 → 升级规则 → 下次检查更准
```

### 4. 机会主义学习 (来自 MetaClaw OMLS)
在"对话空闲期"自动触发学习, 不打扰正常工作流。

## 内循环: 自学习 (来自 MetaClaw + SOLAR)

### 阶段1: 发现分析 (每次检查后)
```
触发: 任何一个体系产生"发现"
↓
分类: 这是新类型? 还是已知类型的变体?
↓
关联: 这个发现和之前哪些发现有关联?
↓
优先级: Tiger > PaperTiger > Elephant > Info
```

### 阶段2: 假设生成
```
如果发现是"编造了技术解释" → 假设: "架构L1缺少对'技术解释编造'的拦截"
如果发现是"同一捷径重复3次" → 假设: "决策审计L2需要升级为强制拦截"
如果发现是"旧知识未被检索" → 假设: "知识管理DECAY率需要调整"
```

### 阶段3: 规则升级
```
假设成立 → 升级具体规则:
  - 新增禁用语 → 架构体系L1
  - 新增KPI → 追踪体系
  - 新增审计方法 → 审计体系
  - 新增决策触发条件 → 决策审计体系
  - 归档新知识 → 知识管理体系
```

### 阶段4: 回测验证
```
新规则对历史对话数据跑一遍回测:
  - 如果是真问题: 之前有多少次能被新规则捕获? (召回率)
  - 如果是误报: 之前有多少次会被错误拦截? (精确率)
  召回率>50% 且 精确率>80% → 生效
  否则 → 调整假设, 重新测试
```

## 外循环: 联网学 (来自 SIA + Hyperagents 跨域迁移)

### 触发时机
- 每个体系产生发现时 → 搜索是否有相关的新研究/工具
- 每10次检查 → 主动搜索各体系领域的最新进展
- 老板说"用skill+检索升级" → 立即触发

### 搜索策略
```
第1轮: WebSearch("[发现关键词] + [体系领域] + 2025 2026")
第2轮: WebSearch("[发现关键词] + alternative approach + latest")
第3轮: 评估搜索结果 → 选出可用的 → 设计集成方案
```

### 注入流程
```
发现新方法 → 评估适配性 → 设计注入方案 → 
在沙盒中验证 → 注入对应体系 → 记录来源 → 
运行回测 → 有效则保留, 无效则回滚
```

### 注入示例
| 联网发现 | 注入到 | 效果 |
|----------|--------|------|
| CoreLogger-AI 实时日志监控 | 追踪体系 | 新增K7自动化指标 |
| Guardian 策略违规检测 | 架构体系 | 增强L1禁用语正则 |
| Cordon 语义异常检测 | 审计体系 | 新增异常检测审计方法 |
| TDKPS 统计漂移检测 | 追踪体系 | K6升级为统计检验 |

## 元认知: 改进"改进本身" (来自 DGM-Hyperagents)

### 每10次自进化后评估
```
1. 统计: 这10次进化中, 几次有效? 几次无效?
2. 分析: 有效改进的共同特征是什么?
3. 调整: 改进方法本身需要改吗?
   - 如果回测总是过于宽松 → 提高生效阈值
   - 如果总是有重复改进 → 加强去重
   - 如果联网学注入率太低 → 调整搜索策略
4. 记录: 元改进历史 → 知识管理体系
```

### 元指标
| 指标 | 含义 | 目标 |
|------|------|------|
| 改进有效率 | 升级后验证有效的比例 | > 70% |
| 新类型发现率 | 发现全新问题类型的频率 | 每周>1 |
| 联网注入率 | 搜索到的可注入方法的比例 | > 30% |
| 回滚率 | 升级后被回滚的比例 | < 10% |
| 跨体系联动率 | 一次发现触发多个体系升级的比例 | > 50% |

## 进化执行卡

```
□ 每次检查后: 内循环 → 发现分析 + 假设生成
□ 每次发现新类型: 外循环 → 联网搜索 + 方法注入
□ 每10次检查: 元认知 → 改进有效性评估 + 方法调整
□ 每50次检查: 全量回测 → 所有规则对历史数据重跑
□ 每次老板纠正: 立即触发全循环(内+外+元)
```
