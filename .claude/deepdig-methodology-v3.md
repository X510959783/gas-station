# 深挖方法论 v3.0 — 闭环修复引擎
# 建立: 2026-05-28 | 基于 Reasoning Loop + ESAA-Security + Dawgen + AIDevOps + AgentForesight
# 替代: 220轮的"发现→不修复→继续发现"病理模式

## 核心转变

```
v2.0(已废弃): 发现→分类→继续发现→460+风险→0修复→发散不收敛
v3.0(当前):   发现→分类→修复→验证→关闭→发现下一个
```

## 6条操作规则（从2026研究提炼）

### 规则1: 原子修复 — Fix + Test + Proof (来自 Reasoning Loop)
每发现一个可修复的风险→立即修复→立即验证→附带修复证据(git diff/命令输出)。
"修复了"不算——修复+测试+证据才算。

### 规则2: 发现/修复比 ≤ 3:1 (来自 Reasoning Loop "cap at 3 corrections per cycle")
每轮最多发现3个新风险。发现3个→必须先修复至少1个→才能继续发现。
这打破了"无限发现→零修复"的病理循环。

### 规则3: 外部镜像 (来自 Reasoning Loop Layer 3)
每周至少一次用不同的模型/视角验证我的审计结论。
单模型自审计存在结构性盲区（NP完全 #31）。外部镜像可以发现自审计遗漏的问题。

### 规则4: 结构化追踪 (来自 ESAA-Security + AIDevOps)
每个风险必须被追踪状态：
  OPEN → ANALYZED → IN_FIX → FIXED → VERIFIED → CLOSED
状态变更附带时间戳和证据。
不再有"发现后遗弃"的风险。

### 规则5: 期望vs现实差异检查 (来自 Reasoning Loop Layer 4)
每轮修复后验证：修复声称的效果 vs 实际产生的效果。
"修复了版本号编造"→验证: git log显示版本号是否已更新。
声称≠实现。和第39条教训(沉默验证)一致。

### 规则6: 老板=断路器+外部锚点 (来自 Reasoning Loop + #44)
老板随时可以：暂停深挖、切换模式、废弃任何规则。
老板的裁决终止递归审计（#44的解决方案）。
不再需要老板说"继续深挖"——我会主动报告状态并等待裁决。
